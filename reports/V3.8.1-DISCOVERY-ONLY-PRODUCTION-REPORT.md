# V3.8.1 — Discovery-Only Production Mode + Cost-Control Amendment

2026-09-03. Builds on V3.1–V3.8 (all preserved, none deleted). Changes the
**default scheduled production path** in response to a real cost incident:
roughly $100 in Claude/API spend over the two prior days of building/
running this pipeline. New operating principle: **CLAUDE DISCOVERS, CLAUDE
DOES NOT ANALYZE.**

## Previous architecture

Scheduled `run_daily.py` → `acquisition_worker.py` (discovery, business
verification, FIT, GAP, buying signals, contactability, deterministic
intelligence, up to 2 specialist agent calls, ranking enrichment, contact
identity — several Claude calls per lead) → deterministic loop (dossier,
asset, outreach draft, QA, send-window planning, `READY_TO_SEND` export) →
`EMAIL_READY`/`CONTACT_FORM_READY` Sheets sync. A wall-clock budget of
2700s and an `outreach_worthy_ceiling` of 15 were the only spend controls;
there was no daily $ ceiling, no cross-invocation cost sharing, and no
call cap independent of research scope.

## New architecture

```
FEDORA / LEAD ENGINE                    CHATGPT + USER
  discover candidates                     qualification
  cheap/deterministic verification        Google/Maps opportunity research
  save candidates                         competitor research
  sync CANDIDATES to Google Sheets        SEO wedge
  STOP                                    contact research
                                           personalized outreach
                                           Gmail execution
                                           reply handling / sales
```

`config/acquisition.yaml: production_mode` is the switch:
`discovery_only` (**default**, what the scheduled timer runs) or
`full_pipeline` (the complete, unchanged V3.5–V3.8 flow above, still fully
callable — never the default again). `run_daily.py` fails closed on any
other value.

## Candidate schema

`schemas/candidate_record.schema.json` — `lead_id`, `business_name`,
`domain` (derived, never a separate fact), `website`, `city`, `state`,
`country`, `niche`, `phone`, `profile_url`, `discovery_source`,
`discovered_at`, `verification_status`
(`CANDIDATE_VERIFIED`/`CANDIDATE_REJECTED`), `basic_business_facts`
(rating/review_count/years_in_business/commercial_value_signal/website-
and-GBP-issue tags — every field nullable, never guessed). **Never**
requires FIT/GAP scores, `maps_position`/`organic_position`, an SEO wedge,
competitor analysis, buying-signal analysis, contact identity, an email,
a dossier, an asset, an email draft, or a send window.

`phone` isn't on the shared `discovered.jsonl` prospect record (V2-era
shape, deliberately unmodified to avoid touching that well-tested path) —
it's carried forward via a small new per-lead artifact,
`data/leads/<id>/candidate_facts.json`, written once at discovery time and
read back by `sync_handoff.py: build_candidate_rows()`.

## Google Sheets CANDIDATES implementation

Additive: `EMAIL_READY`/`CONTACT_FORM_READY`/`RESULTS` are completely
untouched (a dedicated test asserts an EMAIL_READY tab's existing content
survives a candidates-only sync). `GoogleSheetsBackend._upsert_tab()` was
generalized to accept a `columns` parameter (defaulting to the existing
`COLUMNS`, so every pre-existing call site is unaffected) and reused
directly for the new tab — no separate Sheets logic was written.
`config/handoff.yaml: google_sheets.candidates_tab` (default `"CANDIDATES"`,
backward-compatible with a config predating this key) / `local_backend.candidates_file`
(default `"candidates.json"`).

## Idempotency behavior

`lead_id` is the primary identity, exactly like the existing queues.
`GoogleSheetsBackend._upsert_tab()`'s existing column-A lookup means a
rediscovered/re-synced `lead_id` **updates its existing row in place** —
verified against a fake Sheets service (extends the pattern
`tests/test_v3_6_handoff.py` already uses for the RESULTS tab, generalized
to also exercise `update`/`batchUpdate`/`append`) and against
`LocalFileBackend`'s dict-keyed-by-`lead_id` store. `created_at` is
preserved across re-syncs (`handoff_lib.py: merge_candidate_row`); every
other field is Lead-Engine-owned and safe to recompute fresh each sync —
there is no external-write-back concept for a candidate row today.
Deduplication happens even earlier than the Sheet sync: `discover_prospects.py`'s
existing `existing_business_keys()`/`filter_candidates()` (unchanged)
already prevent a rediscovered business from ever reaching
`discovered.jsonl` a second time, so Claude is never even asked to
re-research it.

## Cost control

**Prior context** (user-supplied): approximately $100 in Claude/API token
usage was consumed over the two days preceding this change.

**Daily budget**: `daily_claude_budget_usd` (default **$3.00**), enforced
via `scripts/cost_ledger.py`'s durable, date-keyed ledger
(`data/runtime/cost/<YYYY-MM-DD>.json`, Asia/Karachi calendar day matching
the scheduled timer/catch-up window — gitignored, covered by the existing
`data/runtime/` full-directory `.gitignore` entry). Checked **before**
every Claude call via file-locked read-modify-write, so a 12:00 run that
spends $2.40 leaves a same-day catch-up run only $0.60 — never a fresh
$3.00. A manual retry invocation shares the identical mechanism; there is
no separate manual-vs-scheduled ledger.

**Call cap**: `max_claude_calls_per_run` (default **8**), an independent
circuit breaker that holds even when $ cost cannot be observed at all.

**Runtime cap**: `max_worker_runtime_seconds` (default **600s**), chosen
conservatively against `full_pipeline`'s 2700s — discovery-only never
proceeds past cheap verification, so it needs far less wall-clock room.

**Retry policy**: a real `ClaudeTimeout` on a market-cell discovery call
is retried at most once (`config/discovery_only.yaml: reliability`, same
mechanism as V3.7's `acquisition.yaml`), never for any other error type,
and never for a candidate-level verification failure — a rejected/failed
candidate is recorded and the batch moves on, with zero additional Claude
spend for that candidate (there is no per-candidate Claude call to retry
in the first place).

**Deterministic operations removed from Claude spend**: candidate basic
verification (`candidate_verification.py` — business_name/niche/city-
state/contact-surface presence checks), domain derivation, dedup (already
deterministic in `discover_prospects.py`, unchanged), ID generation
(`slugify`), Sheets/CSV row serialization, and every prospect-record
status transition. The only Claude call anywhere in the discovery-only
path is the existing one-per-market-cell discovery call.

**Expected reduction in Claude workload** (structural, not yet measured
against live traffic): previously, a lead advancing to `CONTACT_FORM_READY`/
`CONTACT_VERIFIED` could involve up to ~6 Claude call classes (discovery,
business verification, buying signals, contactability, 0–2 specialist
calls, contact identity) plus a 2700s wall-clock ceiling and no daily $
cap. Discovery-only mode makes exactly **one** Claude call class (shared
across every candidate a market cell returns), a $3.00/day hard ceiling,
an 8-call/run cap, and a 600s ceiling. I am **not** claiming a specific
percentage reduction — see "What cannot be reliably measured" below.

**What cost information is actually observable**: `claude -p
--output-format json`'s own envelope reports `total_cost_usd` and
`usage.input_tokens`/`usage.output_tokens` for a real, successfully
completed call — `scripts/claude_invoke.py: run_claude_with_meta()`
extracts these (added, non-breaking — `run_claude()` is now a thin
wrapper with byte-identical behavior for every existing caller). When
present, real per-call/per-day $ and token totals are computed and
reported honestly.

**What cannot be reliably measured**: whether a given real environment's
`claude -p` invocation always populates `total_cost_usd`/`usage.*` was not
independently re-verified against live production traffic in this
implementation pass (only inspected in one real preflight-failure log
line from earlier today, which did include `total_cost_usd`/`usage`
fields even for a zero-cost failed call — a good sign, not a guarantee for
every call shape). If a real call's envelope ever omits these fields, this
system reports `cost_observable: false` / `UNKNOWN` for that day rather
than inventing a number, and falls back to the call-count/time governors
as the enforceable proxy — never silently degrading enforcement to "the
target was reached" (candidate count is never the driver).

**Cost-per-verified-candidate measurement**: `discovery_worker.run()`
computes and reports `cost_per_discovered_candidate`,
`cost_per_verified_candidate`, and `cost_per_saved_candidate` whenever
cost is observable for that run (0 candidates never divides by zero — it
reports `None`). This is the primary north-star metric going forward;
real production numbers will only exist after the recommended live
validation below actually runs.

## A safety incident during this implementation, and how it was closed

While writing the first version of `TestRunDailyRouting`, a test called
`run_daily.main()` without redirecting its module-level `DATA`/
`DAILY_RUNS_DIR`/`LOG_DIR` constants (computed once at import time from
the real repo). This (a) overwrote the REAL
`data/runtime/daily_runs/2026-09-03.json` — the actual production run
summary from earlier today (containing a real prospect's diagnosis data)
— three times with fake test data, and (b) let a real, live network
`GET` reach the user's real Google Sheet (`config/handoff.yaml`'s
on-disk, real `spreadsheet_id`), which happened to fail with a transient
503 rather than succeed. No data was ever written to the real Sheet. This
was caught immediately (before reporting completion), and:
1. `data/runtime/daily_runs/2026-09-03.json` was restored byte-for-byte
   from this same conversation's earlier tool output (diffed against the
   restored file to confirm an exact match — zero difference).
2. Three stray test-generated log files were deleted from
   `data/runtime/logs/`.
3. Every `run_daily.py`/`discovery_worker.py` test was rewritten behind a
   new `IsolatedRunDailyMixin` that redirects every real path constant to
   a throwaway `/tmp` directory and forces `config/handoff.yaml` to a
   local-only, unconfigured shape, so no test in this file can ever again
   reach real data or a real network call. A second, distinct bug was
   found and fixed in the same pass: `_lib.py`'s `set_status_everywhere()`
   resolves `PROSPECTS` via `_lib`'s own module globals (it is *defined*
   in `_lib.py`), not the calling module's imported copy — patching
   `discovery_worker.PROSPECTS` alone does not sandbox it; `_lib.PROSPECTS`
   itself must also be patched. This is documented directly in the test
   mixin's docstring so it is never rediscovered the hard way again.
4. The regenerated `data/handoff/*.csv` tracker mirrors (pure, deterministic
   derivatives of the real, unmodified `discovered.jsonl`) were left as
   they were — regenerating them from unchanged source data reproduces
   identical content, so nothing was actually lost there.
5. `reports/report-latest.md`/`triage-latest.md` were confirmed untouched
   (mtimes predate the incident).

Verified after the fix: the full 560-test suite runs end-to-end with every
`run_daily.py`/`discovery_worker.py` log line pointing at a `/tmp/...`
sandbox path, and `data/runtime/daily_runs/2026-09-03.json`'s `run_id`
still reads the real `run-20260903-093350-9994139e` after a full suite
run.

## Limitations

- Discovery-only "basic verification" cannot confirm a website actually
  resolves live (no network fetch is performed — that would itself be a
  research operation this mode deliberately avoids); it checks only that
  a contact surface (website, phone, or GBP URL) was returned by
  discovery. A dead/parked domain could pass basic verification and
  surface in CANDIDATES — exactly the kind of check the ChatGPT+user stage
  is intended to catch next.
- Real cost/token observability from `claude -p`'s envelope was not
  independently re-verified against a live production call in this pass
  (see "What cannot be reliably measured" above) — the mechanism is built
  and tested against the documented envelope shape, but its first live
  exercise is part of the recommended validation below.
- `CANDIDATE_VERIFIED` records are not automatically eligible for a later
  `full_pipeline` run (`acquisition_worker.py`'s `STAGE_A_STATUSES` does
  not include it) — promoting a candidate into the full research pipeline
  is a deliberate future step (e.g. resetting its status), not an
  automatic side effect.
