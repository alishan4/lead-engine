# Lead Engine V3.6 — Shared READY_TO_SEND Handoff Bridge

**2026-09-02.** Adds a shared queue on top of the existing V3.4
`data/outreach/ready_to_send.jsonl` interface so ChatGPT/Gmail-side
automation can consume READY_TO_SEND leads without re-reading raw Lead
Engine artifacts, and so real Gmail-side result events can flow back in.
No Gmail access, no Gmail credentials, no sending anywhere in this phase.
The `READY_TO_SEND` boundary from V3.4/V3.5 is unchanged — this is a
read/write VIEW for ChatGPT, not a new capability for Lead Engine.

## 1. Files changed

**New config**: `config/handoff.yaml` — backend selection, local-backend
paths, Google Sheets adapter settings, the result-event vocabulary, and
tracker CSV filenames.

**New schemas**: `schemas/handoff_row.schema.json` (the 50-column shared
queue row), `schemas/outreach_result_event.schema.json`.

**New scripts**: `scripts/handoff_lib.py` (pure row-building/merge/event-
application functions — the one seam every test exercises),
`scripts/handoff_backend.py` (`HandoffBackend` interface,
`LocalFileBackend`, `GoogleSheetsBackend`), `scripts/sync_handoff.py`
(orchestrator: builds rows from `ready_to_send.jsonl` + lead artifacts,
syncs both queues), `scripts/import_outreach_results.py` (idempotent
external-event ingestion), `scripts/export_tracker_csv.py`
(`leads_master.csv`/`outreach_log.csv`/`follow_up_queue.csv`/
`daily_pipeline.csv`).

**Extended**: `scripts/run_daily.py` (handoff sync + result import +
tracker export wired in right after `export_ready_to_send.py`, before the
reporting exports — wrapped so a total failure never aborts the rest of
the run), `.gitignore` (`data/handoff/*`, mirroring `data/outreach/`'s
pattern — Google Sheets credential filenames are already covered by the
existing `credentials*.json`/`service-account*.json`/`token*.json`
patterns), `CLAUDE.md`/`OPERATING-RULES.md`/`docs/AUTOMATION.md` (the
permanent flow, ownership boundaries, and Google Sheets setup steps).

**New fixtures**: `data/fixtures/example_handoff_row.json`,
`data/fixtures/example_outreach_results.jsonl` (both for the existing
synthetic "Example Roofing Co." business).

**New tests**: `tests/test_v3_6_handoff.py` (26 tests). **325/325 total,
all pre-existing 299 untouched.**

**Not changed**: `data/outreach/ready_to_send.jsonl` and
`export_ready_to_send.py` (V3.4, byte-for-byte the same), every V3.1–V3.4
scoring/routing/QA script, `lead-engine-daily.timer`, `../claude-seo`.

## 2. Backend architecture

```python
class HandoffBackend:
    def export_ready(self, email_ready_rows, contact_form_ready_rows): ...
    def all_rows(self): ...          # {lead_id: row} across both queues
    def import_results(self): ...    # raw external result-event dicts
    def sync(self, email_ready_rows, contact_form_ready_rows): ...
```
`scripts/sync_handoff.py` always writes to `LocalFileBackend` first (the
durable safety net and merge basis), then additionally pushes to the
configured remote backend if it differs from `local`. A remote failure
(`SharedHandoffAuthRequired` or anything else) is recorded and never
raised past this script — the local queue is already written and stays
authoritative, satisfying "if shared sync fails, do NOT lose local
READY_TO_SEND records" without any extra plumbing.

### Local backend

Zero credentials, always available. Two JSON files keyed by `lead_id`
(`data/handoff/email_ready.json`, `contact_form_ready.json` — genuine
upserts, never append-only) plus a CSV mirror of each. Resolves its
directory against `_lib.DATA` (which respects the `LEAD_ENGINE_DATA_DIR`
sandbox override already used by V3.5's controlled-validation pattern) —
**a real bug caught during this implementation's own validation**: the
first version resolved against `ROOT` instead, so a sandboxed validation
run silently wrote into the real repo's `data/handoff/` (harmless, since
the row was the pre-existing synthetic "Example Roofing Co." fixture, but
a genuine isolation defect). Fixed in `handoff_backend.py`/
`export_tracker_csv.py` before this report; re-validated afterward (§10).

### Google Sheets adapter status

**Real, runnable code — not configured in this environment.**
`GoogleSheetsBackend` implements `export_ready`/`all_rows`/`import_results`
against the Sheets API v4 (upsert-by-`lead_id` per tab, batched
update+append), using a service-account credential with **Sheets-only
scope** (never Drive, never Gmail — a separate credential from Gmail's
entirely). Every method calls `_require_configured()` first, which raises
`SharedHandoffAuthRequired` immediately — before any network call — if
`config/handoff.yaml: google_sheets.service_account_file`/`spreadsheet_id`
are unset or the key file doesn't exist. `google-api-python-client`/
`google-auth` are imported lazily inside methods, so this file (and every
test that imports it) works with zero extra packages installed. Full
setup steps are in `docs/AUTOMATION.md` "Google Sheets setup." No
credentials were requested from or provided by the user in this phase, per
the spec — the backend stays on `local` until the user explicitly
provisions one.

## 3. Privacy controls

- `data/handoff/*` gitignored (mirrors `data/outreach/`'s existing
  pattern); `.gitkeep` tracked so the directory structure survives a fresh
  clone.
- Google Sheets credential filenames already matched by `.gitignore`'s
  pre-existing `credentials*.json`/`token*.json`/`service-account*.json`
  patterns — no new pattern needed, verified by test.
- Never public-link-shared: the setup doc explicitly says share with the
  service account's email as Editor, never publish a link.
- No OAuth refresh token, no Gmail cookie/session data anywhere in this
  phase's code — verified by a static grep test
  (`TestNoGmailSurfaceInHandoff`) checking for `smtplib`/`imaplib`/
  `oauth2client`/`google_auth_oauthlib` imports and confirming only a
  `"sheets"` API service is ever built, never `"gmail"`.
- No full-dataset logging: `sync_handoff.py`/`import_outreach_results.py`
  log per-lead one-line summaries, never a full row dump.

## 4. Queue schema

50 columns exactly matching the spec's field list
(`schemas/handoff_row.schema.json`, `scripts/handoff_lib.py: COLUMNS`).
Two ownership groups:
- **Lead-Engine-owned** (business/wedge/asset/contact/email/timing/
  qualification/`lead_engine_state`) — recomputed fresh every sync.
- **External-owned** (`EXTERNAL_OWNED_FIELDS`: `gmail_state`,
  `delivery_state`, `reply_state`, `follow_up_state`, `gmail_message_id`,
  `gmail_thread_id`, `suppression_reason`) — Lead Engine's own sync
  (`merge_row`) never writes these after first creation; only
  `import_outreach_results.py`'s `apply_event` does. This is what makes
  `lead_engine_state` (e.g. `SEND_WINDOW_PLANNED`) structurally distinct
  from `gmail_state` (e.g. `GMAIL_SENT`), and `delivery_state`
  (`NO_BOUNCE_DETECTED`) distinct from a delivery-confirmed claim —
  exactly the "explicit columns instead of one overloaded status" the
  spec asks for.

`sub_niche` is always `null` — no sub-niche taxonomy exists in
`config/niches.yaml` yet, and this phase does not invent one.

## 5. Idempotency

Keyed by `lead_id` (== `prospect_id`) in a dict-shaped store, not an
append-only list — `export_ready` is a pure upsert. `business_id` is the
normalized website domain when known (else `lead_id`), so a future
recycled lead for the same real business is at least identifiable as
related. `merge_row` preserves `created_at`, `last_action`/
`last_action_at`, and every `EXTERNAL_OWNED_FIELDS` entry from the
existing row; only Lead-Engine-owned fields refresh. Verified live: two
consecutive `sync_handoff.sync()` calls against the same lead produce
exactly one row (§10).

## 6. Result import

`scripts/import_outreach_results.py` reads
`data/outreach/outreach_results.jsonl` (+ a configured remote backend's
`import_results()`), applies each event via `handoff_lib.apply_event`, and
logs every attempt (applied or not) to
`data/handoff/imported_events_log.jsonl` for dedup. Two dedup dimensions:
- **Exact duplicate**: `event_dedup_key` collapses the same Gmail
  message/thread id + event_type regardless of `event_at` formatting —
  "never duplicate the same Gmail message/thread event" literally.
- **Stale/out-of-order**: `apply_event` tracks a per-field
  (`gmail_state`/`delivery_state`/`reply_state`/`follow_up_state`/
  `suppression_reason`/`human_review`) last-applied timestamp and refuses
  to apply an event older than what's already recorded for that field —
  "stale Lead Engine data cannot overwrite newer external state,"
  generalized to stale *external* data too.

A `SUPPRESSED` event also registers in the existing V3.3 suppression
registry (`scripts/outreach_lib.add_suppression`) so every other stage of
the pipeline respects it on the next run, not just the shared-queue view.

## 7. Daily sync integration

`run_daily.py`'s chain is now: `export_ready_to_send.py` →
`import_outreach_results.import_results()` → `sync_handoff.sync()` →
`export_tracker_csv.export_all()` → `report_pipeline.py`/
`triage_report.py` — exactly "before the run summary is finalized," per
the spec. The whole block is wrapped in a `try/except` independent of
`sync_handoff.py`'s own internal per-row isolation, so an unexpected crash
in the handoff layer is recorded as `HANDOFF_SYNC_FAILED` in the summary
and never aborts qualification/reporting. Summary fields added:
`handoff_sync_status`, `email_ready_rows`, `contact_form_ready_rows`,
`row_failures`, `import_events_applied`, `import_failures`.

## 8. Reporting exports

`export_tracker_csv.py` regenerates all four CSVs from scratch every run
(never hand-edited, never a transactional path) under `data/handoff/`,
alongside the shared-queue JSON/CSV files. Verified live producing correct
headers/row counts against both the synthetic fixture and a real (0-lead)
production run (§10).

## 9. Tests

325/325 pass. 26 new (`tests/test_v3_6_handoff.py`): eligibility
(email/form/unverified-recipient), merge-never-clobbers-external-fields,
stale-event rejection, duplicate-Gmail-event dedup, `lead_engine_state`
vs. `gmail_state` distinctness, idempotent duplicate export/import,
local-fallback-with-zero-credentials, remote-failure-preserves-local,
per-row failure isolation, no-Gmail-imports/no-Gmail-API-call static
checks, gitignore coverage, tracker CSV generation, and a static guard that
no V3.1–V3.4 scoring file imports any V3.6 module. One real bug was caught
and fixed while writing these tests: a broad `load_yaml` mock initially
made `build_rows()`'s `limits.yaml` lookup return the handoff config
instead, breaking `check_freshness()` — fixed with a filename-aware mock
helper (`selective_load_yaml`), documented in the test file itself so the
mistake isn't silently reintroduced.

## 10. Live / synthetic validation

Real `data/outreach/ready_to_send.jsonl` currently has 0 rows (confirmed
via the V3.5 report), so per the spec, validation used the synthetic
"Example Roofing Co." fixture exclusively:
1. Seeded a sandboxed data copy (`LEAD_ENGINE_DATA_DIR`, the same
   mechanism V3.5's controlled validation used) with the fixture as a
   `SEND_WINDOW_PLANNED` lead.
2. Ran `scripts/sync_handoff.py` for real — produced exactly 1 EMAIL_READY
   row, 0 failures. **This run caught the `ROOT`-vs-`DATA` isolation bug**
   (§2) — the real repo's `data/handoff/` was briefly, harmlessly written
   to with this same synthetic row before the fix; cleaned up immediately,
   fix applied, re-validated with correct isolation confirmed twice more.
3. Ran the real (unsandboxed) `run_daily.sh --dry-run --deterministic-only`
   against the actual repo's current state (16 real prospects, 0 READY_TO_
   SEND) — `handoff_sync_status: SYNCED`, 0 EMAIL_READY/CONTACT_FORM_READY
   rows (correct — nothing is currently eligible), `leads_master.csv`: 16
   rows, `daily_pipeline.csv`: 1 row, no errors. This is the genuine
   "0 real READY_TO_SEND leads today" case working end-to-end.

No real email was sent, no Gmail was accessed, no contact form was
submitted, at any point in this validation.

## 11. Limitations

- **Google Sheets backend is code-complete but unconfigured** — no
  credentials exist in this environment; it has never made a real network
  call. Its contract is covered by unit tests (mocked) and the
  fail-closed path, not a live Sheets round-trip.
- **The remote backend is push-only from Lead Engine's sync perspective**
  — `sync_handoff.py`'s merge basis is always the local store, not a live
  read-back of the Sheet's own edited cells. Result events are ingested
  via `data/outreach/outreach_results.jsonl` (or a `RESULTS` tab through
  `GoogleSheetsBackend.import_results()`), not by treating arbitrary
  in-place Sheet edits as authoritative — a deliberate scope limit, not an
  oversight, avoiding a much larger two-way conflict-resolution design the
  spec didn't ask for.
- **No sub-niche taxonomy** — `sub_niche` is always `null`.
- **`business_id`** is a normalized-domain heuristic, not a true
  cross-time business identity system; a business that changes domains
  would not be automatically recognized as the same `business_id`.
- Zero real READY_TO_SEND leads existed to validate against at write time
  — the local-backend and CSV-export paths are proven against a real
  (empty) production run and a synthetic fixture, not a real outreach-
  ready lead end to end.
