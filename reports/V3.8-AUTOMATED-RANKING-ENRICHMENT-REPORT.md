# V3.8 — Automated Ranking Enrichment

2026-09-03. Builds on V3.7/V3.7.1 (`reports/V3.7.1-RANKING-GAP-SCORING-REVIEW.md`).
Turns `NEEDS_ENRICHMENT` from a queue that only ever grows into one the
daily pipeline actively drains — without lowering FIT/GAP thresholds,
without fabricating a ranking, and without spending one extra dollar of
Claude research to do it.

## Architecture

```
NEEDS_ENRICHMENT (real records only, status filtered defensively)
  -> build_enrichment_queue()      pure, sorted by:
       1. fit_confirmed_score (desc)
       2. gap_potential_score (desc)
       3. niche tier (config/niches.yaml, tier 1 first)
       4. contactability_score (desc)
       5. evidence completeness (desc)
  -> select_queries() per lead     pure, 2-4 queries, config/niches.yaml
                                     money_keywords x city/state, capped by
                                     intended_evidence_type (MAPS/ORGANIC,
                                     only for whichever field is null)
  -> attempt_query() per query     tries the configured provider chain in
                                     order; isolates any provider exception
                                     as a per-query FAILURE and tries the
                                     next provider before giving up
  -> import_ranking_observation.import_observations()   (existing, unchanged)
       for anything a provider returned as a genuinely NEW observation
  -> reevaluate_needs_enrichment.reevaluate_one()        (existing, unchanged)
       for every lead attempted this cycle -- this is what actually reads
       data/rankings/<market_id>.csv, applies whatever's usable, and
       re-runs assess_google_gap.py -> assess_commercial_fit.py
  -> qualify_leads.py --v3         (existing, unchanged) if anything changed
  -> QUALIFIED / HIGH_PRIORITY / MANUAL_REVIEW / REJECTED / still NEEDS_ENRICHMENT
```

Every arrow above except the first two is code that already existed before
V3.8 and is called, never re-implemented. V3.8's actual new surface area is
small and entirely deterministic: prioritize, pick queries, ask a provider,
hand off.

## Provider abstraction

`scripts/ranking_providers.py` defines `RankingProvider` with one method,
`fetch(query_record, freshness_days)`, returning a `ProviderResult` with one
of four statuses — `ALREADY_SATISFIED`, `OBSERVATION`, `RANKING_SOURCE_REQUIRED`,
`FAILURE` — never a fifth, silent "treat missing as poor rank" outcome.

- **`ManualImportProvider`** — reads `data/rankings/<market_id>.csv`,
  already written exclusively by the two existing human-operated CLIs. If a
  fresh (`freshness_days`), validated, query-matched, entity-matched row
  already has the requested field, it's `ALREADY_SATISFIED` — nothing new
  needs importing, the always-run re-evaluation step will pick it up from
  the CSV exactly as it always has.
- **`SemrushFileProvider`** — reads a small, pre-vetted observations file
  (the exact `schemas/ranking_evidence_observation.schema.json` shape
  `import_ranking_observation.py --file` already accepts) that a human/
  analyst drops at `config/ranking_enrichment.yaml: inbox_dir`. Reuses
  `import_ranking_observation.validate_observation()` as the single
  provenance choke point — nothing re-implemented, nothing loosened.
- **`ExternalRankProvider`** — the interface slot for a real, credential-
  backed live rank-tracking API (DataForSEO/SerpApi/ValueSERP/similar).
  **Not implemented.** Always returns `RANKING_SOURCE_REQUIRED`.

### Usable automatic provider: **NO** (by design, in this environment)

I looked at what a genuinely free/zero-cost, fully-automatic, defensible
localized-ranking source would require, per the spec's explicit
constraints:
- Google has no free API for Maps/local-pack or organic rank position.
- Scraping a live Google SERP to infer a rank is exactly the "generic
  WebSearch ordering claimed as a geo-local rank" the spec explicitly
  forbids, and it's fragile/ToS-risky regardless.
- Every real rank-tracking service that could answer this on demand
  (DataForSEO, SerpApi, ValueSERP, SEMrush's own API) is a paid, credential-
  gated product. None is configured in this environment, and V3.8's own
  stop conditions forbid embedding a credential or holding a password.

So `ExternalRankProvider` stays an honest stub, and the two providers that
*are* usable (`ManualImportProvider`, `SemrushFileProvider`) both consume
already-vetted, already-durable evidence rather than fetching anything
live. **What V3.8 actually automates is real and valuable, just narrower
than "fully automatic ranking lookup":** noticing evidence that already
exists or has been dropped, validating it, importing it, and re-scoring —
all zero-Claude, zero-cost, zero-credential.

## Fail-closed behavior

A query with no usable evidence from any configured provider returns
`RANKING_SOURCE_REQUIRED` (exact string) — the honest default, never
converted into a guessed position. A provider that itself breaks (a
simulated timeout/auth/malformed-response/geo-unresolved error in tests;
the shape any future live provider's real exceptions would take) is caught
by `attempt_query()`, recorded as a `FAILURE` for that provider only, and
the chain tries the next provider before giving up — one provider's
breakage never gives up on a query a different provider could still answer,
and a query/lead's failure never blocks another lead or another query
(`tests/test_v3_8_ranking_enrichment.py: TestAttemptQueryIsolation`,
`TestRunCycleBudgets.test_one_leads_provider_failure_never_blocks_another_leads_queries`).

## Backlog prioritization

`build_enrichment_queue()` defensively filters to `status == "NEEDS_ENRICHMENT"`
even if handed a mixed list — `MANUAL_REVIEW` can never enter this queue,
so ranking evidence alone can never auto-qualify a borderline-FIT lead
(`TestManualReviewExcluded`). Sort key, exactly per spec: FIT confirmed →
GAP potential → niche tier (`config/niches.yaml`, tier 1 first) →
contactability → evidence completeness, with a deterministic id tiebreak so
two runs over the same data always agree.

## Cost controls

- `max_enrichment_leads_per_run` (default 8) — bounds how many leads one
  cycle even looks at.
- `max_queries_per_lead` / `min_queries_per_lead` (4 / 2) — bounds per-lead
  query generation; never "dozens of keywords."
- `max_provider_requests_per_run` (24) — a global circuit breaker
  independent of the per-lead cap.
- `freshness_days` (14, kept in sync with `config/limits.yaml:
  ranking_freshness_days` — guarded by a static test) — a stale row on file
  is never silently treated as fresh qualification evidence; it stays in
  history/provenance and the query is treated as still open.
- Zero Claude calls, zero live network calls anywhere in
  `rank_enrichment.py`/`ranking_providers.py` — verified by a static grep
  test (`TestStaticSafetyGuards`). `ranking_cost_estimate` is honestly
  `0.0` every cycle in this environment (nothing here has a real per-call
  cost) rather than an invented number.
- `config/acquisition.yaml`'s existing fresh-discovery caps
  (`max_fresh_candidates_researched_per_run: 10`, `max_fresh_market_cells_per_run: 3`)
  are asserted unchanged by a static test — V3.8 never raises daily Claude
  research just because a backlog exists.

## Limitations

- No automatic, credential-free, defensible localized-ranking source
  exists to plug into `ExternalRankProvider` today — this is an external
  fact about the ranking-data market, not a gap in this implementation.
- `SemrushFileProvider` currently only parses the JSON-observations shape
  (reusing `import_ranking_observation.py`'s validator directly) rather
  than natively parsing a raw Semrush "Organic Research" CSV export's
  column-mapping heuristics — a human can still run `scripts/import_rankings.py`
  directly for that richer format; a future iteration could add a CSV path
  to `SemrushFileProvider` reusing `import_rankings.py`'s existing
  `load_rows`/`normalize_row`/`detect_source` instead.
- Query-to-CSV-row matching (`queries_match`) is a permissive normalized
  substring comparison, not a semantic match — a human hand-typing a
  noticeably different phrasing for "the same" query into a dropped file
  could fail to match. This trades a few missed matches for zero risk of
  conflating two actually-different queries.
- No new JSON Schema file was added for the query-record or run-cycle-stats
  shapes (unlike `ranking_evidence_observation.schema.json`) — both are
  simple enough to document inline; worth adding if this surface grows.

## Recommended live-validation step

Before relying on this in production:
1. Drop one real, already-vetted observation for a real `NEEDS_ENRICHMENT`
   lead (e.g. a manual Google Maps check for one of the 12 above) at
   `data/rankings/inbox/<market_id>.json`, in the
   `ranking_evidence_observation.schema.json` shape.
2. Run `python3 scripts/rank_enrichment.py` once, by hand, and inspect its
   printed stats JSON plus the affected lead's new status — confirm exactly
   one lead moved, its `qualification_v3.json` gained a `ranking_reevaluations`
   entry citing the real source, and every other lead in the backlog is
   untouched.
3. Only after that manual pass looks correct, let a real scheduled
   `run_daily.py` invocation exercise the new stage unattended for the
   first time.

This is the smallest real-data check that exercises the actual write path
(`import_ranking_observation.py` → `reevaluate_needs_enrichment.py` →
`qualify_leads.py`) without trusting synthetic fixtures alone.
