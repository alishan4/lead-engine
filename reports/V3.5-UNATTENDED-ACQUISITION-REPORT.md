# Lead Engine V3.5 — Unattended Claude Acquisition Orchestrator + Same-Day Catch-Up

**2026-09-02.** Turns the existing Tue–Fri 12:00 PKT scheduled run
(`lead-engine-daily.timer`, unchanged) into a real, unattended acquisition
worker. No V3.1–V3.4 scoring, threshold, wedge, or QA logic changed — this
is one new orchestration layer in front of the existing deterministic
chain, reusing every research-stage script's `--print-prompt`/`--save`
contract exactly as it already existed.

## 2. Architecture

```
lead-engine-daily.timer (unchanged: Tue-Fri 12:00 PKT, one production timer)
  -> lead-engine-daily.service (TimeoutStartSec bumped 600s -> 3600s)
    -> run_daily.sh (unchanged: flock on data/runtime/run.lock)
      -> run_daily.py
        -> [NEW] acquisition_worker.run() -- unless --deterministic-only
           - claude_preflight.check() -- fail closed on CLAUDE_AUTH_REQUIRED
           - acquisition.lock (2nd, independent lock for standalone/validation use)
           - pending leads first (Stage A: DISCOVERED..GOOGLE_GAP_ASSESSED;
             Stage C: QUALIFIED/HIGH_PRIORITY..ASSET_STAGED), THEN
           - bounded fresh discovery (config/acquisition.yaml ceilings)
           - every research call -> claude_invoke.run_claude() (--restricted,
             Read/WebSearch/WebFetch only) -> existing script's --save -
        -> qualify_leads.py --v3 (unchanged, bulk FIT/GAP routing)
        -> run_deterministic_scan.py / build_dossier_v3_2.py / stage_asset.py (unchanged, per-lead)
        -> generate_outreach_email.py / qa_outreach_email.py / send_window_planner.py (unchanged)
        -> export_ready_to_send.py (unchanged)
        -> report_pipeline.py / triage_report.py (unchanged)
        -> data/runtime/daily_runs/<Asia/Karachi-date>.json (extended fields)
```

`scripts/acquisition_worker.py`'s job ends at `CONTACT_VERIFIED`/
`CONTACT_FORM_READY` (or a valid stop status short of that) — everything
from there down is the pre-existing, unmodified deterministic code.

## 3. Claude invocation method — the structural safety model

Every research call is:
```
claude -p "<policy preamble + stage prompt>" \
  --restricted --allowedTools "Read WebSearch WebFetch" \
  --permission-mode dontAsk --output-format json \
  --json-schema '<the stage's own schema>' \
  --max-budget-usd 1.00 --no-session-persistence
```
Confirmed empirically (see `claude --help` and three live smoke calls
during implementation) that `--restricted` unconditionally strips Bash/
PowerShell/REPL/other code-execution tools regardless of `--allowedTools`,
confines file tools to the working directory, and refuses
`--dangerously-skip-permissions`. **The invoked process therefore has no
tool capable of sending email, accessing Gmail, submitting a contact form,
or writing any file, under any prompt it could ever receive.** The
orchestrator process — never Claude — performs every file write and script
invocation, via the same `--save -` CLI contract every stage script
already used for a human-driven research pass. `--json-schema` (mapped to
each stage's own documented output shape) plus the CLI's
`structured_output` field replaced fragile ad-hoc JSON extraction.
`--max-budget-usd` is an independent cost circuit breaker under the
worker's own timeout/ceiling logic.

Every prompt opens with an explicit instruction to Read `CLAUDE.md` and
`OPERATING-RULES.md` first (auditable via the Read tool call in the
transcript) — required because each `-p` call is a deliberately
memoryless, fresh session (`--no-session-persistence`, no `--continue`).

**Specialist escalation is the one deliberate fidelity trade-off.** The
interactive `claude-seo:*` Skill packages (e.g. `claude-seo:seo-local`)
require Bash/Write internally. The worker's one absolute invariant — never
grant Bash or Write to any Claude subprocess, under any circumstance — is
never relaxed for this stage either. `ask_specialist()` reuses
`route_to_specialist.py`'s exact routing/capping decision
(`config/opportunity_router.yaml`, hard-capped at 1–2 calls/lead,
unchanged) and `prompts/opportunity-specialist.md`'s framing, but answers
the same narrow, capped question through the same restricted Read/
WebSearch/WebFetch-only profile instead of invoking the Skill package
directly. A specialist finding that would have genuinely required
Bash-based tooling correctly surfaces as low confidence rather than
silently degrading into a fabricated result.

## 4. systemd integration

`lead-engine-daily.timer` is **unchanged** — same `Tue,Wed,Thu,Fri
12:00:00 Asia/Karachi`, still the single production scheduler, no second
timer created. Only `lead-engine-daily.service` changed: `TimeoutStartSec`
600s → 3600s (a run with real Claude research legitimately takes longer
than the ~1s deterministic-only run it used to be; the worker's own
`max_worker_runtime_seconds` (2700s) is the real ceiling, this is the
outer backstop). The updated unit was copied to
`~/.config/systemd/user/lead-engine-daily.service` and
`systemctl --user daemon-reload` run; `systemctl --user list-timers`
confirms the same next-firing time as before (Thu 2026-09-03 12:00 PKT).

## 5. Auth preflight

`scripts/claude_preflight.py` (`claude_invoke.preflight()`): a trivial
`claude -p "Reply only AUTH_OK"` call under the same restricted profile,
45s timeout, $0.05 budget cap. Any exception (`ClaudeAuthRequired`,
`ClaudeTimeout`, `ClaudeInvocationError`) is treated identically — fail
closed, report `CLAUDE_AUTH_REQUIRED`, zero research performed, zero state
touched. Verified live (`AUTH_OK`) before every real run in this report,
and unit-tested for the failure path (mocked).

## 6. Pending-lead processing

Stage A (`DISCOVERED` → `BUSINESS_VERIFIED` → franchise check/escalation →
`assess_commercial_fit` → `assess_buying_signals` → `check_contactability`
→ `assess_google_gap` → `assess_commercial_fit` → `FIT_SCORED`) and Stage C
(`QUALIFIED`/`HIGH_PRIORITY` → `run_deterministic_scan` → specialist
escalation if routed → `build_dossier_v3_2` → `stage_asset` →
`contact_identity`) are driven by `advance_stage_a`/`advance_stage_c`,
each a bounded loop (defensive 15-step cap) that re-reads the prospect
record after every step and dispatches on its current `status` — the exact
state machine the existing V3.1–V3.3 scripts already define, now driven
end-to-end instead of one human-paced step at a time.

**Deliberate exception: `NEEDS_ENRICHMENT`.** This status means
`maps_position`/`organic_position` (ranking data) is missing. The worker
does **not** attempt to fill rankings via Claude — reliable rank-tracking
needs a real SERP-tracking data source or careful manual verification
(`scripts/import_rankings.py`), and "never fabricate rankings" is a hard,
repeated rule. These leads are counted (`needs_enrichment`) and reported in
`limitations`, never guessed past. This is the one place the spec's
"prioritize NEEDS_ENRICHMENT" instruction was traded off against the
stronger, more specific "never fabricate rankings" rule.

## 7. Fresh discovery

`scripts/discover_prospects.py` + `prompts/prospect-discovery.md` +
`schemas/discovery_candidate.schema.json` — the stage that genuinely did
not exist before (per `run_daily.py`'s own prior comment: "no deterministic
discovery workflow exists in this codebase"). Bounded to one
SUB-NICHE × CITY cell per call; `config/acquisition.yaml: discovery_markets`
crosses the spec's named niches (hvac, roofing, restoration, family_law,
plumbing) with 12 fixed mid-size US metros, rotated by day-of-year so a
single run never scans "the whole US" and a cell already present in
`data/markets/` is skipped in favor of a fresh one. Dedupe against
already-known business names/domains (`discovered.jsonl` + `rejected.jsonl`)
happens both in the prompt (told what already exists) and in
`filter_candidates()` (pure function, unit-tested) before anything is
appended. An empty `candidates` array is treated as a fully valid result.

## 8. Commercial-first filtering, daily ceiling, research ceiling, specialist limits

Unchanged from V3.1–V3.2, just now reached unattended: `assess_commercial_fit.py`
runs (twice) before any specialist call is possible; a lead that fails FIT
is `REJECTED` before any GAP/intelligence work, let alone a specialist
call, ever happens. `config/acquisition.yaml` ceilings:
`outreach_worthy_ceiling: 15` (a ceiling, checked via `outreach_capacity_remaining()`
before every discovery cell and every fresh candidate — discovery stops
the moment it's reached, never forced), `max_fresh_market_cells_per_run: 3`,
`max_fresh_candidates_researched_per_run: 10`,
`max_worker_runtime_seconds: 2700`, per-call timeouts (240s research / 90s
short — bumped from 60s after the validation run below observed a real
contactability check land at 60.1s), `max_budget_usd_per_call: 1.00`.
Specialist calls remain capped at 1 (`QUALIFIED`) / 2 (`HIGH_PRIORITY`) by
`route_to_specialist.py`'s own unmodified logic.

## 9. Timeout / failure isolation / evidence handling

`Deadline` (wall clock) is checked before every per-lead/per-cell unit of
work; a call already past deadline never starts. Every stage call is
wrapped in a per-lead `try/except` (`advance_stage_a`/`advance_stage_c`);
one lead's `ClaudeTimeout`/`ClaudeInvocationError`/`RuntimeError` is
recorded in `per_lead_failures` and the batch continues (verified live —
see §11). `call_print()` now raises on a non-zero exit (a real bug caught
during test-writing: it previously would have silently handed a
prospect-not-found/hard-cap error's empty stdout to Claude as if it were a
usable prompt). Evidence states (`VERIFIED`/`UNKNOWN`/etc.,
`schemas/signal_evidence.schema.json`) are untouched — `UNKNOWN != FALSE`
is enforced by the exact same `scripts/signal_evidence.py` resolution code
this worker calls unchanged.

## 10. READY_TO_SEND / catch-up architecture

`data/outreach/ready_to_send.jsonl` and `export_ready_to_send.py` are
untouched. `scripts/catchup.py` (pure functions, `tests/test_catchup.py`)
answers "if invoked right now, what should happen?" for the
12:00–14:00 PKT window using **Asia/Karachi-local date** (not UTC) as the
daily key — a deterministic-only summary (no `acquisition_run_completed`
key) correctly does not block catch-up. **Honest limitation, stated
up front rather than glossed over**: no second timer was added (per
explicit constraint), so this does not add automatic polling between
12:00 and 14:00 — recovering a run that failed mid-window still requires
some manual/follow-up invocation inside the window.

## 15. Limitations

- **No automatic mid-window polling** (§10) — catch-up recovery still needs
  a manual/follow-up trigger inside 12:00–14:00 PKT, by explicit design
  constraint (no second timer).
- **`NEEDS_ENRICHMENT` (ranking data) is out of scope** for Claude research
  by deliberate choice (§6) — stays a manual/CSV-import path.
- **Specialist escalation is Read/WebSearch/WebFetch-only**, not the full
  interactive `claude-seo` Skill package (§3) — a genuine capability
  reduction, traded for an absolute "never grant Bash/Write" invariant.
  Not exercised end-to-end in either live run today (no lead reached
  `AGENT_ROUTED`); covered only by mocked unit tests.
- **Contactability's 90s timeout is still a real constraint** — one real
  call hit the previous 60s cap during validation; bumped to 90s, but a
  slow real check could still legitimately time out and simply gets
  retried on the next run (recorded as a failure, not corrupted state).
- **Discovery quality depends entirely on Claude's live web research** —
  there is no independent verification oracle; the honest-UNKNOWN
  discipline observed in both live runs is a behavior, not a hard
  guarantee, which is why every downstream gate (FIT/GAP/contactability/
  QA) still applies unchanged before anything reaches `READY_TO_SEND`.
