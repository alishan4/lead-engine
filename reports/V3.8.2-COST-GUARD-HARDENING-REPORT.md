# V3.8.2 — Cost-Guard Hardening

2026-09-03. Fixes three real cost-control defects the V3.8.1 first
controlled live validation exposed (same day). Cost-guard hardening
only — no discovery ICP, qualification threshold, V3.8 ranking
architecture, Google Sheets candidate schema, historical lead state, or
Gmail/outreach behavior changed.

## The live incident

The V3.8.1 validation ran 2 real discovery attempts against the live
spreadsheet: 1 succeeded ($0.472659), 1 failed *after doing billable
work* ($0.5358346 — visible in the failed call's own error payload,
consistent with hitting its own `--max-budget-usd` circuit breaker
mid-research). Three defects surfaced:

1. **The daily ledger recorded only $0.472659**, not the true observed
   spend of ≈$1.0084936 — the failed call's real cost was silently lost.
2. **The call counter recorded only successful calls** — `max_claude_calls_per_run`
   would not have stopped a third attempt after the failure, since the
   failed call never incremented it.
3. **Actual wall runtime was 290.1s against a configured 180s cap** —
   the runtime ceiling was checked only *between* market cells, never
   enforced against an in-flight Claude subprocess.

## Root causes

1. `scripts/cost_ledger.py: record_usage()` (V3.8.1) was only ever called
   *after* a successful `run_claude_with_meta()` return, inside
   `discovery_worker.py`'s per-cell `try` block — a failed call raised
   before reaching that line, so its cost/usage were discarded with the
   exception. `claude_invoke.py`'s exceptions also didn't carry any
   cost/usage data at all — even if the caller had wanted to record a
   failed call's cost, there was nowhere to read it from.
2. `CostGuard.calls_this_run` (V3.8.1) was incremented in the same
   post-success-only `record_call()` method — a call cap that, in
   practice, only ever counted successes.
3. The worker deadline (`Deadline.exceeded()`) was checked once at the
   top of each market-cell loop iteration; the Claude subprocess itself
   was always given its full configured per-call timeout
   (`max_claude_call_seconds_research`, 300s), with no awareness of how
   much worker runtime actually remained.

## Changes

### `scripts/claude_invoke.py`
- `ClaudeAuthRequired`/`ClaudeTimeout`/`ClaudeInvocationError` now share a
  `ClaudeCallError` base carrying `.meta` — real cost/usage data recovered
  from the failed call's own output, never fabricated.
- New `_meta_from_text()`/`_first_observable_meta()` helpers: on a
  non-zero exit, `proc.stdout` (then `proc.stderr`) is parsed as a
  `claude -p --output-format json` envelope exactly like the success
  path — a `--max-budget-usd` trip commonly still emits a complete
  envelope reporting the real cost before the CLI aborts. On a genuine
  subprocess timeout, `subprocess.TimeoutExpired`'s own captured
  `.stdout`/`.stderr` are checked the same way (usually empty for a real
  timeout, but never assumed so). On the `is_error`/`error_during_execution`
  envelope path, the already-parsed envelope's own fields are used
  directly.
- `run_claude()`'s public contract is **unchanged** — every pre-V3.8
  caller (verify_business_stage, buying_signals_stage, etc.) sees
  byte-identical behavior; `.meta` is additive, read only by
  `discovery_worker.py`.

### `scripts/cost_ledger.py`
- `record_usage()` replaced by **`start_attempt()`** (reserves an
  attempt and writes a `PENDING` ledger entry *immediately*, before any
  real subprocess is spawned) and **`finish_attempt()`** (enriches that
  same entry with its real outcome: status, cost, tokens, duration, error
  category). A `PENDING` entry that is never finished (a crash/kill) is
  never dropped — it still counts toward `total_calls` and permanently
  marks the day's `cost_observable` false, honestly representing "we
  don't know what this cost."
- Every aggregate (`total_cost_usd`, `cost_observable`, `total_calls`,
  `total_calls_succeeded`, `total_calls_failed`, `unknown_cost_attempts`,
  token totals) is **recomputed from the full `entries` list** on every
  write — never incrementally drifted — so a defensive re-finish or an
  out-of-order write can never corrupt the ledger.
- File-locked (advisory `flock`) read-modify-write, unchanged mechanism
  from V3.8.1 — still the seam that makes the daily ledger shared across
  the scheduled run, a same-day catch-up, and any manual invocation.

### `scripts/discovery_worker.py`
- `Deadline.remaining_seconds()` — new, never negative.
- `CostGuard` rewritten around attempts, not successes:
  `reserve_attempt()` (increments `calls_attempted`, writes the `PENDING`
  ledger entry) / `record_attempt_result()` (enriches it, tracks
  `calls_succeeded`/`calls_failed`/`observed_successful_cost`/
  `observed_failed_cost`/`unknown_cost_attempts`). `check_before_call()`
  now gates on `calls_attempted`, not `calls_succeeded` — a failed call
  counts toward the cap exactly like a successful one, never refunded.
- New **`attempt_claude_discovery()`** — the whole per-cell retry loop,
  rewritten so every governor is checked before **every** real spawn,
  including each retry (a retry is a brand-new `claude -p` process and
  consumes its own attempt slot):
  1. `cost.check_before_call()` (call cap / daily $ budget)
  2. `deadline.remaining_seconds() >= min_seconds_to_start_claude_call`
     — else stop cleanly, never spawn
  3. the subprocess's own timeout is clamped to
     `min(max_claude_call_seconds_research, remaining_worker_seconds)`
  A `ClaudeTimeout` caught with `deadline.exceeded()` already true is
  classified `WORKER_DEADLINE_TIMEOUT` — recorded, never retried, and the
  caller stops the **entire run** (not just this cell), per "no
  replacement/retry call." A plain `CALL_TIMEOUT` (deadline not yet hit)
  is still retried up to `max_timeout_retries`, exactly like V3.8.1.
  `ClaudeAuthRequired` is deliberately **not** caught here — mid-run auth
  loss still propagates and stops the whole run, matching
  `acquisition_worker.py`'s existing rule; the attempt it already
  reserved stays a correctly-unknown `PENDING` ledger entry.
- `empty_stats()`/`CostGuard.summary()` add: `claude_calls_attempted`,
  `claude_calls_succeeded`, `claude_calls_failed`,
  `observed_successful_call_cost_usd`, `observed_failed_call_cost_usd`,
  `observed_total_cost_usd`, `unknown_cost_attempts`,
  `budget_accounting_status`. `cost_per_verified_candidate`/
  `cost_per_discovered_candidate`/`cost_per_saved_candidate` now divide by
  `observed_total_cost_usd` (successful **and** failed known costs), not
  just successful-call spend. V3.8.1's original field names
  (`actual_cost_usd`, `claude_calls`, `cost_observable`) are kept as
  backward-compatible aliases.

### `config/discovery_only.yaml`
- New `min_seconds_to_start_claude_call: 60` — chosen from the live
  validation's own observed timing (the successful call took on the
  order of a minute; the failed one ran 90.9s before its own budget
  circuit breaker fired).
- New comment block documenting the relationship required by Sec.7:
  `max_budget_usd_per_call × max_claude_calls_per_run = $4.00` worst-case
  theoretical per-run exposure, which *exceeds* `daily_claude_budget_usd`
  ($3.00) — the daily ledger, not the per-run call cap, is what actually
  closes that gap in practice; the call cap is defense-in-depth for when
  $ tracking becomes unobservable. **`max_budget_usd_per_call` was
  inspected, not raised**, per explicit instruction — also documented is
  the observed fact that a real call can slightly exceed its own $0.50
  cap (the live $0.5358346 charge), so treating `8 × 0.50` as an exact
  ceiling would itself be false precision.

### `scripts/report_discovery_only.py`
Extended (not replaced) to show: calls attempted/succeeded/failed,
observed cost split by successful/failed calls, `budget_accounting_status`,
and an inline "(INCOMPLETE — N attempt(s) with unknown cost)" note next to
the observed-total-cost line whenever accounting is incomplete.

## Failed-call accounting — the exact live-incident regression

`tests/test_v3_8_1_discovery_only.py`'s `TestCostLedger.test_live_incident_reproduction_success_plus_failed_billable_call`
and `TestCostGuard.test_observed_total_cost_includes_both_successful_and_failed_calls`
reproduce the exact validation numbers end to end:

```
call 1: success, $0.472659
call 2: failure, $0.5358346 (billable — exposed in its own error payload)
-------------------------------------------------------------
observed_total_cost_usd = 1.0084936   (rounds to 1.008494)
claude_calls_attempted  = 2
claude_calls_succeeded  = 1
claude_calls_failed     = 1
budget_accounting_status = COMPLETE   (both costs were known)
```

## Attempt-based call cap

`check_before_call()` now reads `calls_attempted` (incremented the
instant `reserve_attempt()` is called, before any subprocess spawns).
`test_third_call_never_spawns_after_second_call_fails_at_cap_two` proves:
`max_claude_calls_per_run=2`, call 1 succeeds, call 2 fails — a third
attempt is never made, and `dw.run()`'s own `claude_calls_attempted`
stat reads exactly 2.

## Worker-deadline enforcement

Two independent mechanisms, tested separately:
- **Pre-start floor** (`min_seconds_to_start_claude_call`): if less time
  remains than this, no new call is spawned at all —
  `test_call_never_starts_below_minimum_start_threshold`.
- **In-flight clamp**: an already-approved call's own subprocess timeout
  is `min(configured timeout, remaining_worker_seconds)` —
  `test_subprocess_timeout_clamped_to_remaining_worker_seconds` proves a
  40s-remaining call is never given more than a 40s timeout, regardless
  of the configured 300s per-call default.
- A timeout that coincides with the deadline having passed is classified
  `WORKER_DEADLINE_TIMEOUT`, counted, never retried, and stops the whole
  run — `test_worker_deadline_timeout_counted_not_retried_no_replacement`.
  A contrasting test (`test_plain_call_timeout_not_at_deadline_is_retried`)
  confirms an ordinary timeout (deadline not reached) still retries
  exactly as before.

## Unknown-cost behavior

A failed call that exposes no defensible cost still consumes its call
slot (`test_failed_call_with_no_recoverable_cost_marks_attempt_unknown`),
flips `budget_accounting_status` to `INCOMPLETE_UNKNOWN_CALL_COST`
(`test_summary_reports_incomplete_accounting_status_not_hidden_cost`),
and forces `budget_remaining_usd` to `None` — never a confident number —
while the call cap remains the enforceable backstop
(`test_call_cap_and_budget_are_independent_governors`,
`test_budget_remaining_never_exact_when_accounting_incomplete`). A
crashed/never-finished (`PENDING`) attempt is never silently dropped from
the daily aggregates either
(`test_pending_entry_never_silently_dropped_from_aggregates`,
`test_start_attempt_reserves_before_any_outcome_is_known`).

## Limitations / not addressed in this pass

- `min_seconds_to_start_claude_call`'s default (60s) is derived from a
  single live observation (one successful call, one failed call) — it
  has not been validated against a larger sample of real call durations.
- The daily ledger's `PENDING`→never-`finished` crash case is now
  correctly *counted and flagged unknown*, but there is no separate
  "sweep and reconcile stale PENDING entries" tool — a `PENDING` entry
  from a genuine crash stays `PENDING` forever in that day's file (this
  is honest, not incorrect, but a future pass could add an explicit
  "mark abandoned" sweep for operational clarity).
- This pass did not re-run a live validation (explicitly out of scope
  per the stop conditions) — the fixes are verified against synthetic/
  mocked reproductions of the exact live-incident numbers, not against a
  second real `claude -p` call.
